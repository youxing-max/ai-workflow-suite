# AI Workflow Review · 项目级审计

对**项目**（不是单个 diff）做独立健康度审计。审计者必须是 fresh 上下文（subagent 或新会话），不读被审者的推导过程，只读文件与实测。代码级双轴 Review 用 `code-review` skill；本 skill 审的是项目层。

## 三轴

| 轴 | 审什么 | 主要证据 |
|---|---|---|
| Standards | 架构边界、项目规范、安全/隐私实践 | 代码 + ADR + 规范文档 |
| Spec | 需求覆盖：每条 FR/规则可追溯到切片与验收断言；Out of Scope 未被偷做 | project.md + Spec + tasks.json |
| State | 状态可信：文件与实际一致、证据链完整、无伪造迁移、待确认项未过期 | validate_state.py（路径见主 skill「安装与定位」节） + evidence/ + git |

（三轴是本套件的设计：Standards 管代码质量、Spec 管需求覆盖、State 管状态可信度——第三轴针对"多会话长任务"才需要，单独校验。对抗审查的执行方式——fresh 上下文、分诊不判决、误报交人过滤——参考 BMAD 的角色分工。）

## 检查层，不是单道审查

审计的衡量标准不是"有没有人看过"，而是：**这处改动可能出什么问题，哪道检查最便宜地拦住它**。答案应当是一道叠一道的筛子——自检跑测试与构建、界面截图对设计稿、独立上下文双轴审查、安全扫描、机器 Gate（`validate_state.py`）、CI，最底下再垫一层秒级可关的发布回滚。单拎出哪一层都可能漏东西，叠起来才叫防线；某处改动指不出"会被哪道拦住"，就是缺了一层，而不是多找一个人签字。

## 模块审查契约

被审模块应当自带一份**审查契约**（`docs/ai-workflow/review-contracts/<module>.md`，或仓库根的 `REVIEW.md`），由该模块负责人用大白话写，四件事写全就够：

1. **在我这一亩三分地里，什么叫"出事了"**——一句话讲清（例如：文档模块是"它在撒谎"，配置模块是"它指错了路"）；
2. **直接跳过的目录**——不许审查者进场的地方；
3. **细节挑刺上限**——同类小毛病一次最多提几条；
4. **每条发现必须带文件名 + 行号当证据**，拿不出位置的不许写进报告；**确实没问题就痛快来一句"无需修改"**。

契约本身也要短：写得越长，越没人逐字执行。审计中发现代码已经和契约描述不符，**"让契约过期的那处改动"本身就是一条发现项**（标 Standards）。同一类问题反复被误报，改的是契约而不是审查者——源头补短板，比在每轮报告里重复唠叨有效。

## 错题本：事故与回滚都要变成考题

每次线上事故、每次回滚，事后由熟悉那块业务的工程师确认 bug 位置，落成一条回归用例（`docs/ai-workflow/regressions/<日期>-<slug>.md`：现象、最小复现、判定标准、当初哪道检查本该拦住它）。

**改审查规则、改提示词、换工具、换模型之前，必须先把历史用例全跑一遍，分数不涨就不准保留改动。** 没有这道考场，改进全靠感觉，规则退化要等下一次线上事故才发现。

## 步骤

1. 跑 `validate_state.py（路径见主 skill「安装与定位」节）`，红项直接进报告；
2. 抽样核对（至少）：每个 `verified` 任务的 evidence 文件真实存在且对应命令可重跑；`decisions.md` 每条已确认决策有 owner 与日期；`risks.md` 未关闭风险有缓解动作；
3. 审批链抽查：`riskTier` 与 `humanApprovers` 是否达到该档人数下限、名单里有没有把 Agent 算成人类签字、签字之后是否还推过新提交（校验器已核的红项之外，抽 20% 人工复核）；被审模块的审查契约是否存在且与代码一致，`release.md` 记的回滚/事故有没有对应的 `regressions/` 用例；
4. 三轴**分列**报告（不合并、不重排、不互相平均），发现项标 Blocker/Major/Minor + 位置 + 证据，并另标一档性质：**严重 / 顺手改 / 存量**——存量问题开清扫任务，不记在本次作者头上；
5. 报告落 `docs/ai-workflow/audits/<日期>-<slug>.md`，Blocker 同步写入 `state.json.blockers`；
6. 修复后**重跑审计**（认证后改动即失效），直到 0 Blocker；**同一份交付复审最多 3 轮**，第 3 轮仍不清零就停手，把"方案是不是错了"写进 `decisions.md` 交人重审。

## 纪律

- 审计不改业务代码（发现问题开 fix 任务）；
- 对抗式发现是待分诊清单，不是自动判决——误报由人过滤，过滤记录进报告；过滤前先经独立上下文确认（多数认可才进报告），纯风格挑刺与拿不出"文件名 + 行号"的发现不进报告；
- 里程碑收口与项目完结前各至少一次全量审计（见 `/ai-workflow-ship`）；
- 审计自己的规则也算改动：动了套件条款、校验器或审查契约，先跑 `regressions/` 历史用例，分数不涨不准合入。
