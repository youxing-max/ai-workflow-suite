# 复用经验：构建与修订本套件时踩过的坑

来源：2026-10-13 从文章浓缩成 skill、并做三轮独立审计的过程。**只收会反复影响工程判断的条目**，每条给"现象 → 对策"。

## 一、规则与文档写法

**1. 枚举式规则必然漏**
- 现象：修"无人值守"缺口时，用"等人确认 / 等人批准 / 必须由人拍板"枚举替换范围；独立复核连续两轮抓出枚举外形态——"批准……前禁止调用任何实现类 skill"这类**硬门禁句**、以及"由负责人判断 / 需要人过滤"这类**判断式表述**。
- 对策：规则按**类别**写（"所有以人（用户/负责人）为进入下一步前提的表述"），类别内举例而不只举例；改完做一次穷举核对，不要靠抽查。

**2. 环境事实必须实测，不能凭印象**
- 现象：把 `openspec-explore` / `openspec-propose` / `openspec-ff-change` 标成"用户触发"，实测三者 frontmatter 都没有 `disable-model-invocation`（=模型可调用）。
- 对策：写任何 skill 的**调用方式、路径、存在性**之前先 `grep` / `ls` 实测；对照物是磁盘 frontmatter，不是记忆。

**3. 触发假设必须实测**
- 现象：一度把本 skill 设计成"模型可自动拉起"；实跑 omp 时，需求命中 3 个升级信号、skill 也在模型可见列表里，会话记录却 **0 次读取 SKILL.md**——自动路由等于没生效。
- 对策：关键流程的入口不要依赖 description 自动触发；需要人决定"要不要上流程"时，用 `disable-model-invocation` 把入口交给显式调用。

**4. 同名异义要消解**
- 现象："待确认清单"既指澄清阶段要问清的问题清单，又指无人值守下待人拍板的清单。
- 对策：同词异义时加限定词（如"典型待澄清清单"），或在首次出现处注明用途。

## 二、验证纪律

**5. 认证之后任何编辑都使认证失效**
- 现象：审计判定"0 开放项"后又顺手改了两行，原结论就不再覆盖当前版本。
- 对策：改完要么重跑受影响的那个轴，要么显式标注"该修订未经复核"；不要把上一轮的结论套用到新修订上。

**6. 校验脚本自己要自证**
- 现象：独立验收脚本因档位命名（`m6` vs `6m`）适配错误，误判了一个正确实现；凭印象写的 `grep` 模式漏掉中文引号，产生假阴/假阳。
- 对策：先用**已知正样本与负样本**验证检查器本身，再拿它判别人；报告里附上检查器版本与样本。

**7. `set -e` 与"条件 && 动作"会静默中断**
- 现象：校验脚本里 `[ 条件 ] && echo` 在条件为假时返回非零，`set -e` 直接终止脚本——输出被截断，却容易被读成"通过"。
- 对策：校验脚本不开 `set -e`，或一律写 `if`；结尾打印一条"检查完成"作为完整性的凭据。

**8. 作者自评必漏**
- 现象：本次三轮"我以为修好了"，每轮都被 fresh-context 复核抓出一个新的 Major（触发标注误标、版本冲突、无人值守自相矛盾）。
- 对策：规则/文档类改动同样走**双轴独立复核**（fresh context、不读前轮报告、报告分列不合并）；作者只修，不判自己修好了。

**9. 个人解读不能当需求写进验收标准**
- 现象：把"旧版端未请求隐藏就不该降级""新版端应能隐藏等级行"写成硬验收项——实为对歧义需求的个人解读，导致误判了两个合法实现。
- 对策：验收标准标注来源（需求明文 / 我的解读）；解读项按**观察项**处理，不作为通过条件；歧义本身写进待确认清单交人拍板。

**10. 机器门禁的 fail-open 三件套：空容器、null、falsy**
- 现象：三轮对抗审计挖出同一类绕过——`evidence: []` 零迭代当成"有证据"放行；`acceptance: null` 经 `str(None)="None"` 当成非空；`blockedBy: ""` 被 `or []` 静默归一成合法空值；release.md 一个未闭合围栏隐藏其后全部未勾选框。
- 对策：校验代码固定写法"**先归一（None→显式默认）、再类型检查（isinstance）、后业务检查**"；空容器一律按"缺失"处理而不是按"通过"；文档扫描先剥离 fenced 块，未闭合围栏按正文处理（fail-closed）。审计机器门禁必须**逐行通读 + 对抗实测**——文档比对式审计挖不出这类洞（本条即由连续三轮"通读找洞"挖出）。

**11. 形容词需求必须拆成断言，否则实现会默默砍范围**
- 现象：需求"仿 CSDN 个人博客"，Spec 只拆了 API 行为规则；UI 验收停在"HTTP 200 + 元素存在"。交付通过全部门禁与六轮审计，用户一眼判定"太简陋不像 CSDN"，且浏览器端点击行为零自动化证据（"点不进去"类问题全套门禁不可见）。
- 对策：Spec/Plan 阶段把需求里每个形容词（像 X / 美观 / 简单 / 快速）拆成**可检查断言**（结构、行为、视觉基线），拆不了或决定不做的**显式写进 Out of Scope 请用户确认**——隐性砍范围是事故不是节约；用户可见功能的验收必须对齐需求的观察面：HTTP 层断言证明不了 UI 可用与视觉还原，需浏览器级检查（真实浏览器/截图比对）或显式的人工验收步骤（`awaiting_human_evidence`），"测试全绿"不等于"用户看到了效果"。

## 三、实测参考（取舍用）

- 同一棕地需求、同一工具：不用本套件 3.6 分钟交付、用本套件 20 分钟交付（撞所设 20 分钟时限，交付物与审查材料已产出、双轴审查未等完），**功能正确性两者相当**（同一套 9 项独立验收均通过）。差异在过程材料：规则集、落点 ADR、引用式 Handoff、独立双轴审查。
- 结论：本套件买的是**可辩护与可接续**，不是"让实现变正确"；按任务风险决定是否上流程，小任务别硬套。
