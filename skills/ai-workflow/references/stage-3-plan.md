# 第三站 Plan · 任务规划

核心问题：**怎样拆成可独立验证的工作？**（控制任务规模与依赖不确定性）

## 翻车现场：两种死法

**① 任务太大，上下文先崩**：把"完成贵族体系的多端改造"整个当一个任务丢给 Agent——它要同时记住协议、账号、礼物、房间、H5、PC、APP、隐私规则、资源格式、版本依赖和联调顺序。上下文窗口装得下这些文字，不等于模型始终同等重视它们：近期错误和局部实现逐渐占据注意力，早期确认的边界被冲淡——**Context Rot**（Chroma 对 18 个前沿模型的观测：输入 token 增加时性能非均匀下降）。设计边界写得再清楚，不拆小就会在长会话里被稀释。

**② 水平拆分拼不起来**：按技术层分任务——

> ❌ 任务1 改协议 / 任务2 改后端 / 任务3 改H5 / 任务4 改PC / 任务5 补测试

最后一项完成前，没有一个任务形成用户可验证行为；协议和后端各自"完成"，联调时才发现语义不一致。

## 方法

**垂直切片四规则**（to-tickets 的 vertical-slice-rules，每条各防一种死法）：

1. 每个切片切得**窄但完整**穿过每一层（schema、API、UI、测试）——防水平拆分；
2. 完成的切片**能独立演示或验证**——说不清"做完能演示什么"的切片就是没拆到位；
3. 大小以**装进一个全新上下文窗口**为准——上限不是"模型读不读得下"，而是"新会话能不能稳定做完"，直接回应 Context Rot；
4. **prefactoring（预重构）先行**——如"先把进场动效组装逻辑移出特殊玩法分支"，不先做，后面每个切片都绕着旧结构走。

曳光弹（tracer bullet）比喻：曳光弹不追求一击致命，追求"打出去能看见弹道"——每个 ticket 存在的意义是让进展可见、可验证，而不是把工程量均分。

案例切片示例：

> ✅ 切片1 普通直播间进场动效，从协议到 PC webp 展示完整跑通
> ✅ 切片2 本人查看礼物墙：完整数据 + 分界线 + 锁头正常展示
> ✅ 切片3 他人查看设"仅近半年"的墙：只获得范围内礼物
> ✅ 切片4 旧版终端查看隐藏等级的资料卡：按降级规则展示

**Blocking edges**：每个 ticket 显式声明必须先完成哪些 ticket。没有依赖边，并行执行就是赌博，发布顺序靠记性。

**验收标准写成断言**——"给定……当……那么……"：

> 给定墙上同时存在半年内和更早的礼物，当他人查看这面墙，那么响应里只有范围内礼物，且 A 礼物的数量和冠名按累计值展示；本人查看则看到全部礼物和"以下礼物他人不可见"分界线。

注意"数量和冠名按累计值"正是 Brainstorm 记下的易漏规则，在这里变成可检查断言：开发知道实现目标，测试知道观察入口，下一会话不用重新解释什么叫"正确过滤"。

**拆分交人拷问批准**（Plan 阶段的 Gate，别当文书工作省掉——拆分是设计决策，不是誊写）：编号列表展示每个 ticket 的 Title / Blocked by / **What it delivers**（端到端行为，不是任务动作——写不出行为的 ticket 当场暴露切得不对），然后问：粒度合适吗（太粗/太细）？每条依赖是真正的 Gate 吗？要合并或继续拆吗？迭代到用户批准。

## 本地 skill

| skill | 调用 | 用途 |
|---|---|---|
| to-tickets | 用户触发（/to-tickets） | 拆成 tracer-bullet 垂直切片工单，声明 blocking edges，发布到 tracker |
| triage | 用户触发 | issue / 外部 PR 走分诊状态机，产出 agent-ready brief |
| wayfinder | 用户触发 | 超出单会话的大块工作：规划成决策 ticket 地图逐个解决 |
| openspec-apply-change | 模型可调用 | 按 OpenSpec Tasks 清单逐项实施并更新状态 |

## Artifact 与 Gate

- **Artifact**：工单清单 + 依赖边 + 每单验收标准。
- **Gate**：拆分经人批准；每个任务都能独立回答"怎样算完成"（无人值守见 SKILL.md「无人值守模式」）。

## 坑点清单

- [ ] 任务大小按"读得下"定，而不是按"全新会话能稳定做完"定；
- [ ] 水平拆分：各自完成、拼不起来；
- [ ] 跳过 prefactoring，每个切片都绕旧结构走；
- [ ] "v1 先做个基础版"式隐性砍范围（Get Shit Done 的计划规则明确禁止）；
- [ ] blocking edges 缺失，并行与发布顺序靠记性；
- [ ] ticket 只有标题和动作（"修改礼物墙接口"），没有端到端行为；
- [ ] 计划的 verify 不是可自动执行的命令；
- [ ] 省掉人批准拆分这一步。
