# 第四站 Execute · 实现执行

核心问题：**怎样在短反馈里安全实现？当前修改有没有短反馈？**（控制实现过程不确定性）

## 翻车现场：一把梭，然后对着满屏红排查

AI 看到 PRD 就开始全量改文件，一次改十几个，最后才跑完整测试。失败后很难判断哪一步破坏了系统；上下文里同时堆着补丁、日志和猜测，排查质量随之下降。改错模块、删了不该删的、测试挂一片——都是这个节奏的产物。

## 方法：短反馈循环

```
读取当前切片 → 建立可运行的验证入口 → 最小修改 → 立即验证 → 通过后下一片
```

反馈命令四要求：**Agent 能自己运行、失败信息明确、速度足够快、直接覆盖当前切片**。可以是单元测试、契约测试、模块编译，或可重复的最小集成场景。

**TDD 防自证偏差**：测试最后补，Agent 很容易照着刚完成的代码写断言，验证的只是"实现按自己的逻辑运行"。先看到测试因缺少行为而失败，再最小修改让它变绿。协议、跨端资源、复杂 UI 未必适合严格单元测试，可改用契约检查、编译验证或人工联调（无人值守下改选可自动执行的证据形态，如契约检查/编译验证/最小集成场景；若某观察点确实只有人工形态且无法自动替代，该观察点记入待确认清单并显式标注"该验证项未执行"，不得伪造或弱化证据）——但**观察点要在实现前定好**（来自 Design 阶段的 pre-agreed seams，执行阶段不临场发明）。

RED → CHANGE → GREEN 示例（案例真实错误：进场动效组装逻辑写在特殊玩法分支内，能编译、特殊玩法正常、普通直播间永远拿不到资源、无任何报错）：

> **RED**：跑"普通直播间返回进场动效"场景测试 → 失败：响应中没有进场动效资源（证明测试能捕获缺失行为）
> **CHANGE**：把动效数据组装移出特殊玩法专属分支，保留特殊玩法原有行为
> **GREEN**：重跑普通直播间与特殊玩法两组场景 → 都通过（证明当前修改解决了它）

只说"代码已改完"、没有失败到通过的证据，反馈循环就还没闭合。

**验证节奏**（本机 implement skill 的措辞：regularly vs once 的对比）：定期跑类型检查、定期跑单个测试文件、完整测试套件最后跑一次。全量测试留到最后才跑，就是"一把梭"的出处。

**完成边界**（implement 最后两行）：实现完先过 code-review 再提交——"done"在这份 skill 里不等于"完成"，只等于"**可以送审**"；提交到当前分支而不开新分支或推远端，**一个切片的改动 = 一个可回滚单元**。

## 本地 skill

| skill | 调用 | 用途 |
|---|---|---|
| implement | 用户触发（/implement） | 按 spec/tickets 实现：TDD at pre-agreed seams、频繁 typecheck、完成后 code-review 再 commit |
| implement-spec | 用户触发 | 把一份 specification 实现成代码 |
| tdd | 模型可调用 | 测试先行 red-green-refactor |
| diagnosing-bugs | 模型可调用 | 疑难 bug / 性能回归的诊断循环 |
| setup-pre-commit | 模型可调用 | pre-commit 钩子：格式化 + 类型检查 + 测试 |

## Artifact 与 Gate

- **Artifact**：小步 Diff、测试和运行记录。
- **Gate**：当前切片获得**新鲜、可重复**的验证结果；没有证据不推进下一项。

## 出口信号

- 失败反复出现且指向方案本身 → 退回 [Stage 2 Design](stage-2-design.md) 重看边界，别在执行层硬修；
- 切片全绿、证据齐 → [Stage 5 Verify](stage-5-verify.md)：测试只回答测试里写过的问题。

## 坑点清单

- [ ] 一次改十几个文件，最后才跑全量测试；
- [ ] 测试后补，断言照着实现写（自证）；
- [ ] 测试只覆盖特殊分支，普通路径永远不生效且无报错；
- [ ] 执行时临场发明观察点（接缝应来自 Spec）；
- [ ] "代码已改完"就宣布完成，没有 RED→GREEN 证据；
- [ ] 失败反复出现仍在执行层硬修，不退看方案；
- [ ] 一个切片改动跨多个分支/远端，回滚单元破碎。
