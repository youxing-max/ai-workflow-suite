# 第五站 Verify · 验证审查

核心问题：**有什么证据证明做对了？**（控制正确性不确定性）

## 翻车现场："我已经验证过了"

Agent 说"我已经验证过了"——一问，它跑的是自己写的那条顺利路径，边界情况、错误处理、权限路径都没测。这不是撒谎，是**自证闭环**：同一个 Agent 理解需求、设计、写代码、补测试、宣布完成，效率很高，也容易把同一项误解带到每一步。需求一开始读错了，代码和测试可能一起证明这套误解内部自洽。

优雅的代码可能做错需求；功能表面正确，也可能破坏边界、泄漏数据或留下维护负担。

## 方法：双轴独立审查

至少分开检查两个问题：

- **Standards**：代码是否符合项目规范和工程质量要求？
- **Spec**：实现是否满足原始需求？

三个设计点（code-review skill）：

1. **钉死比较点**（commit / branch / tag / merge-base），审一段确定的 Diff——不钉死，AI 容易挑一段对自己最有利的改动来夸；
2. **双轴跑在并行独立 sub-agent 里**，互不污染上下文——防自证闭环的直接手段，独立上下文里误解才有机会暴露；
3. **报告分列呈现（## Standards / ## Spec），禁止合并重排**——一旦合并，"代码写得好"和"需求做得对"混成一项，FAIL 被 PASS 平均掉。只有一个 Reviewer 时也照此分两轮。

**三份证据可以互相矛盾**（案例真实推演）：

| 证据通道 | 检查内容 | 结果 |
|---|---|---|
| 页面自动化测试 | 隐藏礼物卡片没有渲染 | PASS |
| Standards Review | 组件结构、命名、依赖方向符合规范 | PASS |
| Spec Review | 接口响应仍包含隐藏礼物，只是前端没展示 | **FAIL** |

前两个 PASS 洗不掉第三个 FAIL——Brainstorm 写下的"范围外数据不进入接口响应"、Design 定下的过滤位置，在这一刻变成裁决发布的依据。Execute 检查当前反馈，Verify 还要追问：**我们选的反馈足以证明原始需求吗？**

**双轴不是空转的前提**：Spec 来源（原始 issue / PRD）和规范来源（项目规范、架构约定）是前几个阶段的产物。没有这两份输入，Reviewer 拿不出对照物，只能凭感觉说"看着还行"。

**人机分工**：AI 负责扫 Diff、追调用链、跑测试、查异常分支；风险能否接受、需求解释是否正确、哪些问题阻塞发布，由负责人判断（无人值守：误报过滤与风险接受记入待确认清单；Blocker 仍按不可豁免条处理）。对抗式审查有误报——BMAD 官方对 bmad-code-review 也承认这一点，需要人过滤；其结论是分诊清单，不是自动判决。

**证据纪律**（Superpowers verification-before-completion）：任何"完成/通过"的说法之前，必须先运行验证命令并读取输出——"应该能过"不算证据。

## 本地 skill

| skill | 调用 | 用途 |
|---|---|---|
| code-review | 模型可调用，直接加载 | 双轴并行 sub-agent 审查自固定点以来的改动，报告分列 |
| openspec-verify-change | 模型可调用 | 对照变更合同验证实现的完整性、一致性、任务状态 |
| loopforge | 模型可调用 | 重型闭环：双轮审计（作者不审自己、fresh agent、Round 2 禁读 Round 1），从零走交付闭环时用 |

## Artifact 与 Gate

- **Artifact**：测试输出、Spec / Standards Review 报告。
- **Gate**：没有新鲜验证输出，不声称完成；存在未处理的 Blocker，不进入发布。

## 出口信号

- 发现需求遗漏 → 回 [Stage 3 Plan](stage-3-plan.md) 补切片；
- 发现边界/方案问题 → 回 [Stage 2 Design](stage-2-design.md)；
- Blocker 清零 → [Stage 6 Ship](stage-6-ship.md)：代码合并了，交付还没完成。

## 坑点清单

以下错误都能通过编译、局部测试也可能是绿的（案例实录），编译器看不出来，只能对照 Spec、数据流和用户行为审查：

- [ ] 范围外礼物仍在接口响应里，只是前端没渲染；
- [ ] 数量按"近半年"过滤了，但 Spec 要求数量和冠名按累计值展示；
- [ ] 锁头 icon 在他人视角也显示了（Spec 写明只出现在本人视角）；
- [ ] 本人与他人的权限判断写反；
- [ ] 普通直播间进不了特殊玩法分支（进场动效组装被困在其中，普通间永远拿不到资源）；
- [ ] 旧版终端没走降级规则，直接不展示等级行，与 Design 决策不一致；
- [ ] Reviewer 没有 Spec / 规范输入，双轴空转；
- [ ] 两份报告被合并重排，FAIL 被稀释；
- [ ] 反直觉规则没在需求阶段写成断言，Review 时无据可查。

**修订规则/文档类改动同样适用本节纪律**：独立复核、认证后改动即失效、校验脚本先自证——具体踩坑见 [lessons.md](lessons.md)。
