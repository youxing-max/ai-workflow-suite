# 第六站 Ship · 交付沉淀

核心问题：**怎样发布并让后续工作接得上？系统和下一位接手者准备好了吗？**（控制交付与接续不确定性）

## 翻车现场：合并之后，一切归零

**第一种（直接）**：发布只存在于当前对话里——顺序、回滚路径、开关位置全靠口头记忆。于是某个仓库先上线、依赖还没准备好；回滚只做了一半、契约状态不一致；灰度开关在哪只有当时在场的人知道。案例需求跨 11 个仓库、数百文件，靠"协议先合并、下游再升级依赖"的**顺序写在任务材料里**而不是靠记性才走通。

**第二种（安静）**：功能合并了，但没人记得为什么这样设计。下一个需求、下一个会话、下一个同事接手时从头再来；接手者不知道哪些已完成、哪些待联调；任务材料和代码提交对不上；同类错误没进规范，下次继续出现。

## 方法

**① 一页发布计划**：跨仓库/跨终端依赖顺序（协议先发布 → 服务端升级依赖并兼容上线 → 客户端消费新字段）、回滚路径、灰度开关位置——写进仓库，不留对话。**回滚必须是"关开关"而不是"重新发版"**：合并后先挂着开关给内部吃狗粮，确认无异常再往外部流量放；生产出问题，后台一关就退回去，秒级生效，不用等一次发布挤时间窗。`release.md` 里要写清开关在哪、关闭它需要哪一步、关掉之后系统退回什么状态。

**② 最小 Handoff**（不重放整段会话，只说清七件事：当前目标、完成情况、关键决策位置、相关 Spec 与 Diff、验证状态、剩余风险、下一步；下面示例把"决策位置、Spec 与 Diff"两项并进了"依据"一行）：

> 目标：完成"他人查看礼物墙时过滤隐藏数据"切片。
> 已完成：后端过滤、本人/他人契约测试、相关终端联调。
> 依据：需求规则见 Spec；边界决策见 Design；改动链接见任务记录。
> 验证：契约测试和相关回归已通过，输出链接见任务记录。
> 剩余风险：旧版本终端降级展示只验证了主流版本，长尾版本待观察。
> 下一步：上线后跟踪礼物墙客诉与数据复盘；异常时关闭新规则开关并回滚服务版本。

接手者应当能沿着这些引用找到事实、证据和下一动作，无需重读聊天记录——这是 Handoff 的验收句。

四条硬条款（handoff skill）：

- **引用而非复制**：specs / plans / ADRs / issues / commits / diffs 用路径或 URL 引用——复制制造第二份事实源，而第二份总是先过期；沿引用读到的是最新版本，沿复制读到的是快照；
- **存系统临时目录，不放工作区**：工作区是项目共享事实源，交接文档带个人观点和中间态，放进去会被后来的 Agent 当项目材料读进去。交接是临时的，仓库是长期的；
- **带 suggested skills 小节**：交接不只交状态，还交"接下来该调用什么"（接着实现 → /implement，准备收尾 → /code-review），下一位直接被接回工作流而不是从零猜；
- **脱敏并按用途裁剪**：API key、密码、个人身份信息在这一步拦下；调用参数是下一会话的重点，据此裁剪内容——交接不是压缩比越高越好，是让下一位能立刻开工。

**③ 经验回流有筛选标准**：只收**会反复影响工程判断**的内容——可见范围过滤在服务端完成；普通直播间能力不塞进特殊玩法分支；身份关系由拥有完整上下文的边界层判断；旧版本兼容用降级不硬撑。某次需求的临时字段、具体日期、一次性排期没有长期价值。**规范库什么都收，最后会成为上下文垃圾场**。

**④ PRD 末尾留两个固定位置**："本次迭代遗留问题"（因排期/技术原因没做完的事留档，如特权详情图待更新、规则页待过审、各等级权益需逐项核对）+ "数据复盘"。**交付不是代码合并那一刻结束的，是这些尾巴都被书面接住之后才结束的**。

**⑤ 熔断器：回滚率抬头就收紧门槛**。审批减负的前提是有一道保险丝兜底——`release.md` 里记了一次回滚或线上事故，下一里程碑的人工审批档位整体上调一级（`low`→`medium`→`high`），并强制一次全量审计（`/ai-workflow-review`）；解除收紧必须由人确认并记进 `decisions.md`，不许自动恢复。**这道保险丝没装上之前，不要把更多改动放进零人工审批通道**：省下来的是排队时间，赌上去的是线上事故。每个事故与回滚同时进 `regressions/` 错题本（见 `/ai-workflow-review`），下次改审查规则或换模型时拿它们考一遍。

**两种记忆**：Trellis 的 Journal 维护"过程记忆"（上次做到哪了：做了什么、改了哪些文件、提交哈希、下一步，进 Git）；OpenSpec 的 archive 维护"规范记忆"（系统现在约定成什么样：增量折回 openspec/specs/ 长期规范，变更档案按日期留存）。长期项目多人多工具接力，两个半边都要。

## 本地 skill

| skill | 调用 | 用途 |
|---|---|---|
| handoff | 用户触发（/handoff） | 把当前对话压缩成交接文档（存临时目录、引用不复制、含建议 skills、脱敏） |
| claude-handoff | 用户触发 | 直接把工作交给一个全新的后台 agent 立即接手 |
| retro | 用户触发 | 对一次 coding session 做复盘 |
| openspec-archive-change | 模型可调用 | 归档完成的 Change，增量规范折回长期事实源 |
| release-openspec | 模型可调用 | 发布流程：审计合并工作、changesets、切版本、验证发布 |

## Artifact 与 Gate

- **Artifact**：PR、发布计划、Handoff、经验回流记录。
- **Gate**：发布和接续路径闭环——交接存在、引用有效、敏感信息清零。

## 时机提醒

Handoff 不是 Ship 专属：**跨会话任务在任何阶段都可能需要 Handoff**，上下文将满就写，不必等到发布前。

## 坑点清单

- [ ] 发布顺序 / 回滚路径 / 开关位置只存在于对话和在场者脑子里；
- [ ] 交接文档塞进工作区，被后来的 Agent 当成项目材料；
- [ ] 交接复制大段 Artifact 内容，制造先过期的第二份事实源；
- [ ] 泛泛总结全部历史，没按下一会话用途裁剪；
- [ ] 密钥 / 个人身份信息跟着交接文档扩散；
- [ ] 遗留问题不留档，等客诉来发现；
- [ ] 经验回流什么都收，规范库变垃圾场；
- [ ] 任务材料和代码提交对不上，接手者考古聊天记录。
